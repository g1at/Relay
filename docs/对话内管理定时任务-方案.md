# 对话内查询/修改定时任务 — 方案（调研 OpenClaw + Relay 落地）

> 需求：在聊天框里说「我有哪些定时任务」「把每日股市新闻改成每天8点」「删掉整理A股那个」，让 AI 直接查/改/删。
> 本文先把 OpenClaw 的真实实现挖出来，再给 Relay 的落地方案 + 取舍。

---

## 一、OpenClaw 怎么做的（已扒源码确认）

下了 OpenClaw 仓库 tarball 实读，核心文件 **`src/agents/tools/cron-tool.ts`（843 行）**。结论：

### 它就是「给 agent 挂一个 cron 工具」
- **单一工具 `cron`，带 10 个动作**（不是每个操作一个工具）：
  `status / list / get / add / update / remove / run / runs / wake`
- 模型在对话里自主调用这个工具完成增删改查。比如用户说「列出我的定时任务」→ 模型调 `cron({action:'list'})`。
- 工具的 `handler` 里 `switch(action)`，每个动作 **`callGateway('cron.xxx', ...)`** —— 因为 OpenClaw 有**常驻 Gateway 守护进程**，工具只是「调 Gateway API 的薄壳」，真正的 cron 状态/调度都在 Gateway 进程里。

### 给模型看的工具描述（关键，决定模型会不会用、用得对不对）
原文（节选）：
```
Manage Gateway cron jobs and wake events: reminders, check-back-later,
delayed follow-ups, recurring work. Do not emulate scheduling with exec sleep/process polling.

ACTIONS:
- status: scheduler status
- list: jobs; includeDisabled true includes disabled
- get: one job; needs jobId
- add: create job; needs job object
- update: patch job; needs jobId + patch
- remove: delete job; needs jobId
- run: trigger now; needs jobId
- runs: run history; needs jobId
- wake: send wake event

JOB SCHEMA (for add): { name, schedule{...}, payload{...}, delivery{...}, sessionTarget, enabled }
SCHEDULE TYPES: at{at} / every{everyMs} / cron{expr,tz}
  Write expr in local wall-clock time; do not convert to UTC first.
  Example 6pm Shanghai daily: { "kind": "cron", "expr": "0 18 * * *", "tz": "Asia/Shanghai" }
```
要点：① 动作清单 + 每个动作要什么参数，写得极清楚；② JOB SCHEMA 内联给出；③ 反复强调「cron 用本地时间别转 UTC」「别用 sleep 模拟调度」。这些是模型能正确使用的前提。

### 它依赖什么（Relay 没有的）
- **常驻 Gateway 守护进程** + Gateway 内的 cron 子系统（工具只是 RPC 客户端）。
- 模型能稳定进行**工具调用**（OpenClaw 不绑特定模型，走各家 provider，工具调用可靠）。

## 二、Relay 的处境（为什么不能照抄）

| 维度 | OpenClaw | Relay |
|---|---|---|
| 架构 | 常驻 Gateway 守护进程，cron 在进程内，工具走 RPC | 单进程 Electron，cron 在 `scheduler.js`（main 进程内），无 Gateway |
| 模型链路 | provider/model，工具调用可靠 | headless `claude -p`，走 **mify 网关**；记忆 [[reference-openclaw]]/[[relay-spinner-hang-diagnosis]] 实测：**mify/mimo 撑不住派生调用 + 复杂工具链，子 agent/WebSearch/WebFetch 全挂** |
| 工具机制 | 内置工具直接挂 agent | Relay 给 `claude -p` 挂自定义工具 = 得写 **MCP server**（stdio），且 headless 每轮新 spawn、MCP 握手有延迟（飞书 MCP 就因此踩过坑） |

**直接照搬 OpenClaw（给模型挂 cron MCP 工具）的风险**：
1. mify 网关大概率**扛不住这种带工具循环的对话**（你已多次踩到）。
2. 写操作（改/删定时任务）交给模型自主执行，**误删/改错风险高**，且 headless 下没法弹确认框。
3. MCP server 要新建 + 注册 + 每轮握手延迟，复杂度和已有飞书 MCP 那套坑叠加。

## 三、Relay 落地方案（三选一）

### 方案 A：照抄 OpenClaw —— 给 `claude -p` 挂 cron MCP 工具
- **做法**：写一个本地 stdio MCP server（如 `relay-cron-mcp`），暴露 `list/get/add/update/remove/run` 工具，内部读写 `schedules.json`（或通过 IPC 调 scheduler）。在 `claude:run` 时注册进 `--mcp-config`。
- **优点**：最「智能」，模型自主决策，能力对齐 OpenClaw。多轮自然对话（「那个改成8点」「再加一个每周一的」）模型自己接得住。
- **缺点**：① **mify 网关高风险**（工具循环可能挂）；② 写操作模型自主、headless 无法二次确认，**误操作风险**；③ 新建 MCP server + 注册 + 握手延迟成本。
- **适用**：等 Relay 接了能稳定跑工具循环的模型档（如官方 Pro 链路）再上。**当前网关下不推荐。**

### 方案 B：意图识别拦截（复刻现有「自然语言建任务」那套）⭐推荐
- **做法**：扩展现有 `sched:detectIntent`（已落地、已验证）的意图集——从只识别「**建**任务」扩到识别「**查/改/删/启停/立即跑**」：
  - 渲染层先正则快筛（含「定时任务/任务/提醒」等词才进）；
  - 命中 → 调 haiku 抽结构化意图 `{op: 'list'|'update'|'delete'|'toggle'|'run'|'create', 目标任务的指代, 改动内容}`；
  - main 进程**直接操作 scheduler**（不经模型自主），按 op 分发：
    - `list/query` → 回一张**任务列表卡片**（复用现有卡片样式，直接在对话里展示）；
    - `update/delete/toggle/run` → 先**模糊匹配**目标任务（按名称/描述），回一张**确认卡片**（「要把『每日股市新闻』改成每天08:00？[确认][取消]」），用户点确认才执行。
- **优点**：① **稳、不依赖网关工具循环能力**（只用一次 haiku 抽意图，和建任务同款，已验证 mify 扛得住）；② 写操作走**确认卡片**，可控、防误删；③ 复用大量现成代码（detectIntent、确认卡片、scheduler CRUD）；④ 和你已经用顺的「自然语言建任务」体验一脉相承。
- **缺点**：① 不如 A「智能」——复杂多轮指代（「刚才那个」「第二个」）需要额外处理；② 意图集和匹配逻辑要逐个写（list/update/delete/toggle/run）。
- **适用**：**当前 Relay 网关下的最佳选择。**

### 方案 C：纯按钮化，不做对话控制
- 只做需求①（弹出式管理框做漂亮），对话里不查不改。
- 最省事，但没满足你「对话里查/改」的核心诉求。**不推荐**（你明确要对话控制）。

## 四、推荐：方案 B，分两阶段

**阶段 1（先做，覆盖 80% 价值）：查询 + 启停 + 立即运行**
- 这些是「只读/低风险」操作，识别到就直接执行/展示，体验最顺：
  - 「我有哪些定时任务」「列一下定时任务」→ 列表卡片
  - 「暂停每日股市新闻」「启用那个」→ 确认后 toggle
  - 「现在跑一下整理A股」→ 确认后 runNow
- 复用 `detectIntent` 加 op 分支 + 列表/确认卡片。

**阶段 2：修改 + 删除（写操作，强确认）**
- 「把每日股市新闻改成每天8点」「删掉整理A股那个」
- 模糊匹配目标 + 改动解析 + 确认卡片（明示改动前后）。
- 删除/改时间这种破坏性操作，确认卡片必须清楚展示「改什么、从什么变成什么」。

**配套**：需求① UI 弹出式管理框（仿「库」的模态），与对话控制并行做，互不依赖。

## 五、与 OpenClaw 对照（方案 B 达成度）

| OpenClaw cron 工具能力 | Relay 方案 B | 达成 |
|---|---|---|
| list / status | 识别「查询」→ 列表卡片 | ✅ |
| get | 识别「看某个任务详情」→ 详情卡片 | ✅ |
| add | 已有（自然语言建任务） | ✅ |
| update | 识别「改」→ 匹配+确认+update | ✅（带确认，更安全） |
| remove | 识别「删」→ 匹配+确认+remove | ✅（带确认） |
| run | 识别「现在跑」→ 确认+runNow | ✅ |
| runs | 识别「看执行历史」→ runs 卡片 | ✅ |
| 模型自主多轮工具循环 | 单次意图抽取，复杂指代需额外处理 | ◐ 降级 |
| wake（唤醒心跳） | Relay 无 Gateway 心跳概念 | ✗ 不适用 |

> ✅ 对齐 ｜ ◐ 部分 ｜ ✗ 不适用

**结论**：方案 B 用「意图识别 + main 直接操作 + 确认卡片」在 Relay 当前网关下**稳妥复刻** OpenClaw cron 工具的查/改/删/跑能力，且写操作更安全（强制确认）。唯一降级是「模型自主多轮工具循环」——但那正是 mify 网关扛不住、且写操作风险最高的部分，降级反而更稳。
