## 方案 1：定时 chat 任务注入长期记忆

**现状**：`execChat`（scheduler.js）把 `action.prompt` 裸传 `runClaudeJob`；`buildMemoryHint()` 只拼在交互聊天路径（main.js `claude:run` 处理器）。而 `runClaudeJob` 核心已**无条件** `--add-dir MEMORY_DIR`（main.js:627-629）——模型有目录权限，只是没人告诉它记忆库存在。

**设计**：

- `buildMemoryHint(mode)` 参数化：
  - `'full'`：现状（索引 + 读规则 + 写规则），交互聊天继续用；
  - `'read'`：定时任务默认。索引 + 读规则 + 一句「这是无人值守的定时任务，只读取记忆辅助本次执行，**不要写入或修改**记忆文件」；**空库时直接返回空串**（省 token，无人值守也没什么可教的）；
  - `'off'`：返回空串。
- `initScheduler` 的 deps（main.js:2209）增加 `buildMemoryHint`。
- `execChat` 拼接：`prompt + deps.buildMemoryHint(memMode)`，`memMode` 取 `task.action.memory`，缺省 `'read'`，可选 `'off' | 'read' | 'readwrite'`（readwrite → 'full'）。
- cron-mcp-server 的 create/update 工具 schema 加可选 `memory` 字段，对话里能说「这个任务不要用记忆」。

**为什么默认只读**：每日新闻类任务一天跑两次，写权限放开的话，模型偶发把当日新闻当「值得长期记住的事实」写库，日积月累污染记忆。读是普惠的（个性化），写是危险的（污染），`readwrite` 留给方案 3 的整理任务和用户显式要求。

**风险与对策**：
- 每次运行 prompt 多 ≤8KB → 对日频任务可忽略；空库零开销。
- 记忆里的 feedback 类条目（如「回答要简短」）会改变任务输出风格 → 这正是注入的目的；个别任务不想被影响，设 `memory:'off'`。

**决策点**：默认 `'read'` 是否认可？`memory` 字段要不要暴露到 UI（建议先不，对话/MCP 能改就够）。

## 方案 2：失败自动重试

**现状**：`fireTask` 失败只记 `lastStatus/lastError` + 通知，下一次执行要等下个计划触发点。网络抖一下，当天 9 点的新闻就没了。

**设计**（复用单 timer 架构，不开新 timer，重启也存活）：

- 失败且 `enabled` 且 `kind ∈ {cron, every}` 且非手动运行 → `task.retryCount = (task.retryCount||0)+1`；
  - 若 `retryCount ≤ MAX_RETRY(=1)`：`task.nextRunAt = now + 5min` 落盘 → 单 timer 自然到点重跑。重试窗口里关了应用，启动补跑同样兜得住（nextRunAt 已过 → missed 补跑）；
  - 否则放弃：保留 pre-run 已推好的网格 nextRunAt，`retryCount = 0`（下个计划触发点重新获得重试预算）。
- 成功 → `retryCount = 0`。
- `runNow` 手动运行不触发自动重试（用户在场，自己会再点）：`fireTask(id, { manual: true })`。
- `at` 一次性任务**不**自动重试，保持「跑完归档」语义简单；失败已有通知可见。
- 通知文案区分：首次失败 →「执行失败，5 分钟后自动重试」；重试再失败 →「执行失败（已重试 1 次）」。
- UI（可选 2 行）：`retryCount > 0` 时「下次」后面加「(重试)」，避免用户看到非整点时间困惑。

**⚠ 与今日抖动修复的交互**：`init()` 启动时会清掉 cron 任务的未来 `nextRunAt` 重排（修正旧版 5 分钟抖动残留）。挂起的重试点也是「未来的非网格 nextRunAt」，会被误清 → **必须加条件：`retryCount > 0` 的任务跳过清理**。

**决策点**：MAX_RETRY=1、延迟 5 分钟，先硬编码还是开 `schedule.retry` 配置字段？（建议硬编码，有真实需求再开。）

## 方案 3：记忆自动整理（consolidate as a scheduled task）

**现状**：记忆只增不整。注入预算注释写着「超了说明该 consolidate」，但没有任何 consolidate 机制；UI 只能手动单条删。

**设计**：把整理本身做成一个**内置定时任务**——两个功能互相成就，也是 dogfooding：

- 固定 id `builtin-memory-consolidate` 的 chat 任务：`memory: 'readwrite'`，默认 `cron: 0 4 * * 0`（周日 04:00），`delivery.saveToHistory: true`（审计报告免费落历史会话）。
- 入口在 **设置 → 记忆** 面板：
  - 「自动整理」开关：开 = 创建（或启用）该任务；关 = 禁用。任务在定时任务弹窗里照常可见、可立即运行、可删（完全透明，无隐藏魔法）；
  - 「立即整理」按钮：创建后 `runNow`（不开开关也能单次手动整理）。
- 整理 prompt 要点（写死为常量，非用户可编）：
  1. 通读记忆库全部 .md（MEMORY.md 除外）；
  2. 同主题合并：保留信息量大的文件，把另一份的增量并入后删除另一份；
  3. 已过期/被证伪的删除；**拿不准的一律保留**（保守原则）；
  4. 删除/合并前，必须把被删内容的要点写进本次整理报告（报告落历史会话，可审计可手动追回）；
  5. 不碰 MEMORY.md（系统自动重建）。

**安全护栏（无人值守删改记忆是本方案最高风险动作）**：默认关、opt-in；报告落历史可审计；prompt 内置保守原则；记忆面板本来就能查能改能恢复。另：模型经 Bash 删文件的能力随任何 chat 任务本来就存在，本方案无新增攻击面。

**决策点**：默认关（建议）还是装好就开？周期默认周日 04:00 合适吗？

## 方案 4：记忆索引两级降级（规模问题，可缓）

**现状**：索引 >8KB 时只注入最近 40 条完整行，更老的记忆对模型「不可见」（它不知道该 Glob 什么关键词）。

**设计**：降级时改为两级——最近 40 条保持完整「name — description」行；**其余条目只列 name**（逗号分隔，每条 ~30 字节），加一句「需要时按 name Read 对应文件」。几百条规模下全部记忆至少名字可见。

**建议**：当前才个位数条目，远未触发降级。可顺手做（~10 行），也可等方案 3 上线后观察是否还需要。

## 方案 5：cron 时区 —— 建议不做

本地时区对桌面个人工具是**正确语义**（用户说「每天 9 点」就是墙上时钟 9 点）。自写零依赖 cron 引擎要支持 tz-aware 需引入 IANA 时区数据或 Intl 换算 hack，复杂度/收益严重不成比例。OpenClaw 有 cron+tz 是因为它是服务端守护进程。记录为已知取舍；真出现需求（跨时区出差、与服务器对表）再评估。
